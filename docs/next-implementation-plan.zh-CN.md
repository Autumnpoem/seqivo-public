## 5. 验收、看板和交付规则

每项按“建立复现/基线 → 实施 → 定向测试 → 必要的构建与集成 → 独立审查 → 用户流程核对 → 记录交付”推进。权限、进程生命周期和数据迁移须由实现者之外的人复核；两次有依据的修复仍失败时先重新判断原因。

卡片默认只展示：**已做到什么、还差什么、下一步操作**。例如：

> 已能从手机进入原终端并切换会话。还需验证更换设备后默认是否一致；下一步在电脑把 B 设为默认，再从手机主动连接，确认进入 B 且原程序仍在运行。

详情里的每条待办包含操作步骤、通过条件、环境/版本、结果与证据。圆圈切换只表示用户办结该条待办，不自动把测试改为通过，也不代替对应版本的人工验收。

每批交付后，更新实际看板、测试摘要、受影响文档和私有 GitHub；私有服务器地址、凭据、数据库与原始私有输出不上传。只重验受变化影响的范围，不清空无关的历史结论。

每个工作包由一个实现负责人负责收尾；权限、停止、接管、恢复和迁移由另一位审查者检查实际改动与证据。客户端、后端和验证可按互不重叠的文件及测试环境并行，不用多角色数量代替交付结果。

一批可交付的条件为：明确的功能入口可用、受影响检查通过、失败/恢复路径有记录、安装包与服务版本对应、看板剩余项已具体化。无法验证的环境单独标注，不将模拟器等同实体手机，不将本机通过等同线上已部署。

当前编写计划无需补充配置。实施遇到系统解锁/设备授权、无法远控的真机操作、缺少目标系统或签名条件时，说明具体阻塞和最少配合步骤；其余可独立工作继续进行。

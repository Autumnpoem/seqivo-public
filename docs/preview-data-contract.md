# Preview data contract: `records-v1`

This is the first dynamic preview target for a disposable Web project. Its page must call a real, persistent records API: create a record, reload the page, and read that same record back. The target is a fixed `records-v1` adapter backed by private SQLite, not a URL supplied by a project or an arbitrary HTTP proxy. The private SQLite module implements atomic record receipts; the v2 Hub/Core routes and Board iframe handshake are implemented in this slice and require the integration checks below. The adapter is not an arbitrary HTTP backend proxy.

## Trusted registration and storage

Only the local Core owner may register an immutable Vite build and select `apiTarget:'records-v1'`. Core generates a fresh `dataStoreId`; it must never trust one supplied by a browser, Hub, or build. Registration binds `{previewId,projectId,taskId,contentVersion,artifactDigest,dataStoreId}` to one private data store. `dataStoreId` is an opaque storage identity, not a secret or authorization credential. The first slice assigns a distinct store to each preview; a new build does not silently adopt the old build's data. The dynamic manifest needs a new explicit protocol version and the exact target/store/scope fields. Core reads task, project directory, content version and node ownership before import, then repeats those checks after awaited import and immediately before local bind and Hub registration. Hub validates that its registered manifest, node ownership and Core store scope match exactly; no side may infer the dynamic target from `dataMode`. A v1 static manifest remains static, while a v1 dynamic manifest or v1 dynamic node frame is rejected. Registration retains the existing source commit, dirty digest, artifact digest, environment, and declared `dataMode`. The UI must describe `dataMode:'real'` as persistence in this disposable project's local SQLite store, not proof of a production service. Imported build bytes remain an import fact, not verified build provenance.

`createPreviewRecords({dbPath,now})` currently exposes synchronous `bind(scope)`, `list(scope)`, `createOperation(scope,operation)`, `readOperation(scope,operation)`, `reconcileOperation(scope,operation)` and `close()`. **Every record write must call `createOperation`; there is no raw record-create API that can bypass an operation fence.** The module accepts trusted, already-authorized scope only. `bind` is idempotent for the exact identity; reuse of a preview or data-store ID with different identity fails. Titles are trimmed (1–120 well-formed Unicode characters, at most 480 UTF-8 bytes, no control or format characters) and mutation IDs accept 1–100 `[A-Za-z0-9_-]` characters. Isolated UTF-16 surrogates are rejected because SQLite otherwise round-trips them as U+FFFD; ordinary emoji are valid. At most 200 records exist per preview. `list` returns `{records:[{id,title,createdAt}]}` in creation order. The module does not grant access based on `dataStoreId`, open a port, or run project scripts. Network callers must perform all account, project, node, capability, and version checks independently.

The storage operation object is exactly `{operationId,tenantId,actorUserId,clientMutationId,payloadHash,admission:{nodeId,nodeEpoch,connectionGeneration,admissionSequence}}`; only `createOperation` also takes `title` in that object. `payloadHash` is lowercase SHA-256 of `JSON.stringify({title:trimmedTitle})`, checked again at creation. `admission` is the **original persisted write-admission identity**, never an assertion that a restarted or replaced connection is currently authorized. A future caller must independently validate its current authenticated link and the original Hub admission before calling these methods; it must not rewrite `connectionGeneration` to the new link's value. The ledger uses globally unique `operationId` and a unique `(previewId,dataStoreId,tenantId,actorUserId,clientMutationId)` key. Any rebind of operation ID, actor, scope, key, payload or original admission is rejected. `createOperation` returns `{operation:{id,status:'confirmed',record:{id,title,createdAt}}}`; `readOperation` returns the same known outcome or `{operation:{status:'unknown'}}` without writing. `reconcileOperation` inserts a permanent `not_applied` fence when no operation exists **and no matching internal record exists without a receipt**, returning `{operation:{id,status:'not_applied'}}`; a late create of that exact operation is rejected. If a matching record exists without a receipt, reconciliation returns 503 `PREVIEW_RECORD_INTEGRITY`, leaves the record intact and reports no false non-execution proof. The inverse damaged state—a `not_applied` fence alongside a matching record—also returns 503 on read, reconcile and attempted create; it is never reported as a proved non-execution. Record insertion and confirmed receipt, or a new non-execution fence, each commit in one transaction in the same private SQLite database. An exact confirmed retry returns the same record; a different actor with the same external key gets a distinct internal mutation identity.

The persistent operation ledger has hard production bounds of **1,000 rows per preview/data-store scope and 100,000 rows per database**, counting both confirmations and permanent fences. A new create or reconcile that would add a row at either bound returns 429 `PREVIEW_RECORD_OPERATION_LIMIT` without writing a record, receipt or fence; an unanswered prior request remains unknown to the client. Existing operation reads, exact confirmed retries, and existing fence checks still work at the limit. Neither confirmations nor fences are pruned to make capacity, because deleting a fence could allow a delayed original write. Isolated tests may inject smaller positive limits, never values above these production maxima.

Hub applies the same 1,000-per-preview and 100,000-total limits inside its write-admission transaction. The global check counts every durable Hub operation row, including an unresolved admission, confirmation or non-execution fence; it occurs only after the exact original-key lookup, so existing history and confirmed retries remain available when full. Hub does not prune uncertain or terminal operations to free space.

## Narrow network API

| Request | Successful response | Notes |
| --- | --- | --- |
| `GET /api/previews/{previewId}/data/records` with `X-Seqivo-Preview-Data: {dataCap}` | `{records:[{id,title,createdAt}]}` | Exact registered `records-v1` target only. |
| `POST /api/previews/{previewId}/data/records` with the same header and `{clientMutationId,title}` | `{record:{id,title,createdAt},operationId}` | JSON only; cap body at 4 KiB. A confirmed exact retry returns the existing record. `operationId` is not required to recover a lost response. |
| `GET /api/previews/{previewId}/data/stores/{dataStoreId}/operations/by-key/{clientMutationId}` using an account session | `{operation:{id?,clientMutationId,state:'confirmed'|'not_applied'|'unknown',recordId?}}` | Same original account and current project grant. Missing Hub row returns 404, which remains **unknown** to the client; GET never creates a record or a fence. |
| `POST /api/previews/{previewId}/data/stores/{dataStoreId}/operations/by-key/{clientMutationId}/reconcile` with `{}` | Same operation envelope | Explicit original-operation reconciliation. It may persist a Hub and/or Core `not_applied` fence; it never creates a record. |

The existing static site capability remains read-only. A separate random 32-byte `dataCap`, stored only as a hash, is minted atomically with the current preview access intent only for a registered dynamic target. It expires no later than the intent's ten-minute lifetime and binds to its exact preview/build, login session, account, project, target and permitted methods. A viewer may read only; an owner with current project access may write. Hub uses the existing account session row to check that the original session is still active; the iframe never receives its Cookie. Local Core has no account-session identity: its data cap is bound to the local bearer role and service boot ID, and every restart invalidates it. Neither surface treats a role check as project access on the other surface.

The browser receives no Hub account or node token. The Board appends only a nonsecret nonce and public scope IDs to the iframe URL fragment. After checking the current iframe window and scope, the Board sends the data capability in a one-time in-memory `postMessage`; it never places the capability in the URL or durable browser storage. Fetches use `credentials:'omit'` and the dedicated header; the data cap is never an Authorization bearer for general Hub APIs.

The HTML remains an opaque-origin CSP sandbox without `allow-same-origin`. The actual Board iframe bridge appends only a nonsecret launch nonce and public scope IDs in the fragment; the data capability is delivered by a strictly checked parent message, never in a URL or persistent browser storage. Project JavaScript must echo that nonce and wait for the parent's durable save ACK before POST; a standalone iframe lacking the Board bridge cannot write. Only a registered `records-v1` build may add the Hub origin to `connect-src`. Only the exact data route may answer `Origin: null` with narrow CORS for `GET`, `POST`, and `OPTIONS` preflight allowing only `Content-Type` and `X-Seqivo-Preview-Data`; use `Vary: Origin`, no wildcard or credential allowance, and no general Hub API CORS change. The route rejects Cookie and Authorization headers, checks its hashed data capability and original active login session, and rechecks capability, user/session, project grant, preview identity, node epoch and target binding after awaits and before response bytes. The Core node handler independently checks the registered build and exact scope. It accepts only structured `records-v1` operations over the existing outbound WSS channel; it never accepts a URL, local path, SQL or arbitrary method from Hub. Bound response size, concurrency, timeout and errors.

### Write admission, closure, and recovery

Before sending POST, the opaque iframe requests a save identity from the Board parent. The parent validates the exact current iframe window, preview/store/project/account, access generation and fresh nonce; it verifies the current account, computes the canonical payload hash, durably stores `{previewId,dataStoreId,clientMutationId,originalAccountUserId,projectId,payloadHash}` on the Board origin, and only then ACKs the original key. If persistence fails, the iframe must not POST. The data capability is sent to that iframe only in memory and never stored. Recovery GET/reconcile is issued by the Board parent under its current account session, not by the opaque iframe. `clientMutationId` is a random, client-known operation key, while the server-generated `operationId` is an internal correlation ID that may never reach the client. The client must not generate a replacement mutation ID for the same Save action while the original is unknown. Hub also refuses a new mutation for that account and preview/store while any earlier write is unresolved, so changing the ID cannot bypass recovery.

Hub keeps a durable operation row with opaque random `operationId`, original `clientMutationId`, canonical payload hash, preview/store scope, original account user/session, node ID/epoch and connection generation. Its unique operation/fence key is `(tenantId,originalAccountUserId,previewId,dataStoreId,clientMutationId)`; a different account's same mutation string is a different operation. Under one SQLite write transaction, Hub checks an active cap and current authority and inserts the row in `admitted` state, unless a matching row or fence already exists. **That transaction commit is the write-admission linearization point.** It changes to `dispatched` only when its authenticated node frame is sent. An exact repeat can consult the same operation; changed payload is 409. Core stores tenant and original account user IDs in its operation receipt and passes `SHA-256(JSON.stringify([tenantId,actorUserId,dataStoreId,clientMutationId]))` as the bounded internal `clientMutationId` to the current storage module, so two users cannot alias its per-preview mutation key. The external mutation ID remains intact in Hub/Core operation receipts for by-key lookup.

`POST .../access-intents/{intentId}/close` atomically revokes both static and data caps and closes the intent in the Hub database. **That transaction commit is the no-new-write-admission linearization point.** Close currently returns immediately: `{inactive:true,dataWrites:'settled'}` if no operation under that session remains unsettled, otherwise `{inactive:true,dataWrites:'unknown'}`. It does not wait for an admitted operation. A pre-close admitted write **may commit after close**; the original browser request then receives 403 on its final cap check, while account-authenticated by-key recovery can still report the committed record. `inactive` means no new read or write may enter, not that an earlier write was undone. Unknown outcomes retain their operation rows for reconciliation.

The v2 node `records-create` frame carries `{v:2,type:'records-create',requestId,scope,operation}`. The exact scope fields are `{previewId,projectId,taskId,contentVersion,artifactDigest,dataStoreId}`; the operation fields are listed above and include the original node admission identity. Hub persists admission before sending. Core checks the authenticated current link, exact registered scope, project authority and original operation identity, then stores record and receipt atomically. That one admitted operation may finish after cap closure; it grants no new mutation. The node returns `records-result` or `records-error` with the same request ID. Hub accepts only its matching live node/request pair, checks the operation ID in the result and updates the matching durable row. Replaced-link or late replies cannot confirm a different operation. V1 frames cannot exercise this route.

The authenticated Hub recovery routes first verify the caller's current account, tenant and project grant against the exact registered preview/store. If a row exists, the caller must be its **same original account user**; a new session for that user may inspect history but cannot reuse the old session's cap. A different user, revoked grant or replaced store receives no original operation content. If no row exists under the caller's own scoped key, GET returns 404 and the client remains `unknown`: the Hub may have restored a backup after dispatch while Core retained a write. An explicit reconcile with no Hub row also remains `unknown`; it does not create a fence or authorize a replacement mutation. A v2 Hub dispatches only after its admission row commits, but absence of that row after restore is not a continuity proof. Only an existing admission with its original operation, actor, node connection and scope may be reconciled with Core. A replaced node/connection or unavailable Core result remains `unknown`.

For an admitted/dispatched row, Hub reconciles the original `operationId`, actor, scope and mutation hash with Core; it never sends `records-create` again. Core's operation/record transaction either finds the matching committed record or commits a permanent `not_applied` fence before returning absence. Any late original frame then fails against the Core fence. Hub persists `confirmed` or `not_applied` only from that exact Core receipt; an offline node, changed Core store identity, mismatched frame or absent old-protocol proof stays `unknown`. Repeat GET/reconcile returns the same terminal fact. Neither path starts a new write or changes the mutation ID. The client may start a new Save action with a fresh ID only after it has resolved the original action and explicitly chooses to do so.

The local desktop adapter has no Hub account/session and must not pretend otherwise. Its equivalent by-key recovery uses the original `previewId/dataStoreId/clientMutationId` and current local owner bearer; the original short-lived data cap dies on boot change. Core-side operation receipts and fences now survive a storage-module restart in the same private database. The module itself does not authenticate a live link: Hub and Core must perform those checks at their network boundaries. A lost Hub admission after backup restore cannot be fenced from absence and remains unknown. Independent security review and the full fault matrix below remain required before calling this product slice fully verified.

Expected errors use the existing JSON error envelope: invalid body 400 `PREVIEW_RECORD_INPUT`; missing target 404 `PREVIEW_NOT_FOUND`; invalid, expired or revoked data cap 403 `PREVIEW_DATA_AUTH`; changed payload 409 `PREVIEW_RECORD_CONFLICT`; record or operation limit 429 `PREVIEW_RECORD_LIMIT` / `PREVIEW_RECORD_OPERATION_LIMIT`; offline node or uncertain receipt 503 `PREVIEW_RECORD_UNKNOWN`. A recovery GET 404 `PREVIEW_RECORD_UNKNOWN` is not proof of non-execution. Responses must not contain a capability, local path, SQL text or arbitrary backend output. The narrow HTTP/WSS routes are implemented; independent security and end-to-end fault review remains pending.

## Required integration verification

`tests/e2e/preview-records-live.mjs` uses a disposable Vite build in real Chrome with Core+Hub: Save reaches the real records API, reload reads the same record, and an intercepted POST whose real Hub/Core response is deliberately lost is recovered by the original Board-stored mutation ID. `tests/preview-records-live.test.mjs` covers local and Hub routes, owner/viewer permissions, invalid and cookie-bearing data requests, changed payload, an admitted write that commits after close but whose old cap cannot return bytes, post-close admission denial, and Core/Hub restart reads. Storage receipt/fence ordering and capacity are covered by `tests/preview-records.test.mjs`. Remaining independent review should examine changed grants/accounts, node replacement during every await boundary, local boot invalidation, and the full 200-record limit. These are verification gaps, not proof that the implemented route is unsafe or complete.

Independent security review of the implemented network route and narrow CSP/CORS change is required before product acceptance.

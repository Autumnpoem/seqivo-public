# Preview protocol v1

This is the first Core/Hub implementation contract. It serves an immutable Vite production build with client-side interaction. The build must use Vite `base: './'`. Live login/data endpoints, arbitrary HTTP proxying, development servers, and source-map browsing are outside v1. `dataMode` is a local owner declaration (`real` or `simulated`), not independent proof of a data source. The public manifest always reports `capability:'static-interactive'` and `backendApi:'unsupported'`.

## Core and Hub wiring

`createPreviewRegistry({dataDir})` in `server/preview/registry.mjs` imports an already built `distDir` with `register({projectId,taskId,contentVersion,projectDir,distDir,environment,dataMode})`. Registration does not run project scripts or read Hub credentials. It computes the Git commit and dirty digest, hashes every asset, rejects symlinks and limits the tree to 1000 files, 32 MiB total and 4 MiB per file, and copies files into a private snapshot. `get(previewId)` returns the internal manifest; `read(previewId,relativePath)` checks its hash again. The caller must give this module a trusted local owner context and a build directory belonging to the selected project.
The registry data directory must be outside that source checkout so its snapshots cannot feed back into the source fingerprint.

The artifact digest identifies the exact bytes served; the Git identity identifies the source checkout when those bytes were imported. This import alone cannot prove that a preexisting `distDir` was built from that checkout. The UI must label both values separately. A later controlled build runner requires an OS boundary before it executes untrusted Vite config or package scripts near board credentials.

`POST /api/preview/builds` is a local Core owner-only route. The body is `{projectId,taskId,contentVersion,distDir,environment,dataMode}` and the response is `{preview:publicManifest}`. Core verifies that the task belongs to the bound project, that its current content version matches, and that the project is selected for the connected Hub node. It imports the build and waits for Hub registration. The browser-facing manifest never contains `distDir` or another local path.

The desktop board also exposes the same `/api/previews` list, detail, retest, draft and confirm routes through its loopback HTTP server. These routes use local owner/viewer bearer credentials, never a Hub account cookie or the node credential. Owner-only feedback confirmation writes a real task through the same atomic Core receipt. The local HTML and asset URLs use a separate ten-minute read-only build capability so an iframe needs no bearer. This capability is held only in local server memory and expires on server restart; the desktop UI can request a new detail URL. The phone uses the Hub routes and its existing account cookie. Drafts made on one surface are stored at that surface, while confirmed tasks appear in the shared Core task list after synchronization.

`createPreviewNodeLink({registry,credentials,createFeedbackTask})` reuses `remote.terminalCredentials()` shape `{url,token,nodeId,epoch}`. Core refreshes the link after identity changes. The link initiates WSS to `/api/preview/node` on the configured Hub host and port. It answers `get` only for a locally marked Hub-registered `previewId` and a relative asset path; it never accepts a URL or local absolute path. The registration receipt is persisted in the private snapshot so approved builds remain readable across Core restarts. It also handles bounded `create-feedback` messages for the exact locally registered preview identity. Core closes the link during shutdown.

`createPreviewHub({store,accounts,secure,publicOrigin,now,createTask})` exposes `async handleHttp({req,res,method,path,body,send})`, `handleUpgrade(req,socket,head,{allowedHosts,allowedOrigins})`, and `close()`. The Hub HTTP server awaits it before the generic Hub route and dispatches Preview and Terminal upgrades through **one** server upgrade listener. The Preview module creates its own SQLite tables in the shared Hub DB; it does not change existing Hub tables.

On first feedback confirmation the Hub rechecks the account's owner role and project permission, persists the dispatch state and original recovery identity, then sends `create-feedback` over that preview node's WSS channel. The node verifies the registered preview identity and current local project selection. Core calls `Store.createPreviewFeedbackTask`, which commits the task, keyed receipt and permanent outcome in one SQLite transaction. A repeated Core operation with a proven outcome returns that same task only while its original feedback binding still matches. The Hub does not resend a persisted uncertain confirmation after restart: the browser must query or explicitly reconcile the original operation. `createTask` remains an optional injection seam for isolated contract tests. The Hub never marks old human acceptance as passed or failed.

## Browser HTTP API

All list, detail, feedback, and HTML entry requests require an existing account session cookie and project access. Bearer account substitution is denied. Feedback requires owner role and exact same-origin `Origin`. Responses use the existing Hub error envelope when routed through `handleHttp`.

| Route | Response / effect |
| --- | --- |
| `GET /api/previews?taskId={taskId}` | `{previews:[publicManifest]}`; at most 30, filtered by tenant and project access. |
| `GET /api/previews/{previewId}` | `{preview:publicManifest,launchUrl,expiresAt}`. `launchUrl` embeds a random, 10-minute, read-only static resource capability; it contains no account or node token. |
| `POST /api/previews/{previewId}/access-intents` | Exactly `{}` → `{intent}` in `registered` state. Registers one access attempt without creating a resource capability. |
| `POST /api/previews/{previewId}/access-intents/{intentId}/issue` | Exactly `{}` → `{intent,preview,launchUrl,expiresAt}`. Issues once; a repeat is rejected rather than minting or returning another link. |
| `GET /api/previews/{previewId}/access-intents/{intentId}` | `{intent}` without a resource capability. Reads the original attempt after a lost response. |
| `POST /api/previews/{previewId}/access-intents/{intentId}/close` | Exactly `{}` → `{intent,inactive:true}` only after a terminal `closed`, `expired`, or `invalidated` state is verified. Closing a registered attempt prevents a late issue request. |
| `POST /api/previews/{previewId}/revoke` | Exactly `{capability}` → `{revoked:true}`. Requires the same current user and login session that minted this link, project access, and same-origin `Origin`. Local Core binds the link to the minting bearer role. This revokes only this link, not the build or another login's links. |
| `GET {launchUrl}` | Serves the immutable `index.html` only to the same authenticated user who requested the capability. Static relative assets under the same capability URL are hash-checked and may be fetched by the sandboxed document. |
| `POST /api/previews/{previewId}/feedback` | `{pagePath,summary,criterionIds?,idempotencyKey}` → `{feedback:{id,previewId,status:'draft',taskId:null,pagePath,summary,criterionIds}}`. `pagePath` accepts `index.html`, `/index.html`, or a safe relative page route without traversal. Same key and identical body return the same draft; changed body returns 409. No task is created. |
| `POST /api/previews/{previewId}/feedback/{feedbackId}/confirm` | First explicit confirmation dispatches a real Core task; returns `{feedback:{id,status:'confirmed',taskId},verification,retest:{items:[],reason:'awaiting_new_preview'}}`. A known confirmed record returns the same ID. A persisted uncertain dispatch returns `409 PREVIEW_FEEDBACK_UNKNOWN` instead of sending again. |
| `GET /api/previews/{previewId}/feedback/by-key/{idempotencyKey}` | Reads the original draft operation and its verification state. Missing record returns 404, which does not prove non-execution. |
| `POST /api/previews/{previewId}/feedback/by-key/{idempotencyKey}/reconcile` | Exactly `{}`. Reads an existing operation, or transactionally records a non-execution fence against a late draft request. Does not create a task. |
| `GET /api/previews/{previewId}/feedback/{feedbackId}` | Reads the persisted original feedback and verification state; does not dispatch or redispatch creation. |
| `POST /api/previews/{previewId}/feedback/{feedbackId}/reconcile` | Exactly `{}`. Queries the original Core outcome or safely fences an unsent creation where the original protocol and store identity permit it. Does not create a task. |
| `GET /api/previews/{newPreviewId}/retest?previous={oldPreviewId}` | `{previousPreviewId,previewId,items:[{criterionId,text,status:'needs_retest'\|'unknown',reason}]}` for the same project/task. Criteria explicitly linked by confirmed feedback need retest when the build changes; other impact remains unknown. Identical artifact/environment/data mode returns an empty list with `reason:'same_artifact'`. |

`publicManifest` has `previewId,projectId,taskId,contentVersion,sourceCommit,dirtyDigest,dirty,artifactDigest,environment,dataMode,capability,backendApi,createdAt`. It contains no local path, node credential, account cookie, or raw build files. Hub accepts node registration only if the node's current epoch owns the project and a fresh snapshot contains the task with the same `contentVersion`.
`environment` is a declared display label of at most 80 UTF-16 characters. Unicode, including the desktop default `本机静态构建`, is supported; empty labels and control/format characters are rejected.

Revocation is idempotent while an unexpired revoked record remains retained; an expired or pruned record is rejected. Revoked links do not consume active-link capacity (20 per Hub user, 100 per local Core). Hub retains at most 200 revoked records per user; local Core retains at most 200 in total. After an awaited asset read, the Hub rechecks the link, minting account session, user/project access and exact node connection/epoch; local Core rechecks the link and build registration before returning bytes.

The current panel registers an access intent before requesting a link. Its explicit close, version switch, refresh and return close that same intent, including when the issue response is still pending or lost. Registration, issue, status and close waits have an eight-second UI deadline; this deadline does not cancel or undo a server operation. If an intent ID was received, the user can query or close that attempt without issuing again. If registration itself is unknown, no issue request was sent and no capability was created by that request. A status response saying `issued` does not contain the lost link: close the old attempt before explicitly requesting a new one. A missing record, denied request or timeout never proves that access was revoked. Late issue responses cannot restore a closed iframe. List refresh completes before the panel selects and signs a refreshed version.

Each intent has a random 43-character identifier, exact preview/project/task identity, state and expiry. Hub binds it to the current user and the exact login session; local Core binds it to the owner/viewer role and service boot. Issue and close state changes are transactional. Hub closure survives restart; a local restart invalidates old active intents rather than reviving in-memory capabilities. Intents expire after ten minutes, with at most 20 active and 200 terminal records per subject; terminal records are retained for a bounded recovery window. Expired or pruned IDs cannot issue again. Both successful and error responses must match the original scope before the UI uses them.

Navigating elsewhere in the outer app or closing the browser does not guarantee a confirmed revocation; the existing short expiry and session revocation remain applicable. Previously downloaded bytes cannot be recalled. Feedback creation has a separate operation identity: closing an access intent does not prove whether a feedback task was created.

## Feedback recovery

Recovery responses bind `feedback` to `previewId`, `projectId`, `sourceTaskId` and `contentVersion`, with the original feedback `id` when one exists. `verification.state` describes what is known about that original operation, not whether the user has accepted the resulting work:

| Feedback status | Verification state | Meaning |
| --- | --- | --- |
| `draft` | `not_requested` | This new-protocol draft has not been dispatched; an explicit first confirmation may proceed. |
| `confirming` | `unknown` | Dispatch may have occurred; query or explicitly reconcile, without resending creation. Old draft records with uncertain dispatch history are exposed this way. |
| `confirmed` | `confirmed` | A matching created-task receipt is known. |
| `created_unavailable` | `confirmed` | Creation is known, but its matching task is no longer available; do not recreate it. |
| `not_applied` | `not_applied` | A durable fence proves that this original operation cannot execute later. A new report requires an explicit new action. |

If reconciliation contradicts an already known creation, the Hub retains that history and reports verification `unknown`; it does not replace it with `not_applied`. Clients keep input locked on contradictory or unrecognized combinations. A 404, timeout, missing permission, offline node, capacity limit or different Core store never means that the original operation did not run.

Hub recovery is scoped to the current user, preview and authorized project. New clients also send `X-Preview-Actor-Id` on feedback requests, derived from `/api/auth/me`; a different current account returns `409 PREVIEW_ACTOR_CHANGED`. This header is a consistency check and never replaces cookie authentication. Legacy clients may omit it. Authorization is checked again after awaited confirmation/reconciliation before a result is returned. Local owner recovery uses the local bearer role; viewer credentials cannot create or reconcile feedback.

Before dispatch, the Hub atomically changes only a new `draft` (`protocol_version=0`) to `confirming`, recording the original node recovery protocol and `recovery_store_id`. Concurrent requests in that process may await the same in-memory operation, but a restarted process cannot resend a persisted `confirming`. Legacy protocol-1 draft history is uncertain and likewise requires reconciliation. A node advertises recovery protocol 2 and a persistent Core store identity internally over WSS. Only the original protocol-2 operation on the same store can prove an absent operation will never execute by committing a non-execution fence. An existing matching creation receipt remains usable without inventing a new dispatch.

Core outcomes have no task foreign key: deleting a task does not erase the fact that it was created. Creation and its outcome are atomic; non-execution fences reject a late create. Reads and repeated creation also compare the present task's feedback identity, project and canonical payload hash, so a restored, unrelated task with the same ID cannot impersonate it. Journal/archive restore in the same database retains outcomes; rolling back the entire database to an older backup does not promise retention of later facts. Local preview history retains its manifest so source-task deletion does not silently erase the original operation identity.

Draft records and draft-key fences share a limit of 200 per preview/user (per preview on local Core). At capacity, a previously unknown key cannot be fenced and remains unknown; no success is fabricated. Recovery metadata saved by the client contains operation IDs, account/project/task/version identity and result references, never credentials, full preview URLs or feedback text. Saving that identity must succeed before sending. Reloads only read the original operation; explicit reconciliation may close it against a late request. Multiple tabs must preserve already confirmed facts and must not reopen a draft when an older response arrives.

Protocol unit tests live in `tests/preview-feedback-recovery.test.mjs`. The browser test below injects response loss at the network boundary against real services; it is not a physical-phone outage test. Final App and installation-package coverage remains separate in PLAN-09.3.

The real browser regression can be run after a local build with `SEQIVO_TEST_DIST_DIR=dist node tests/e2e/preview-access-live.mjs`. It starts isolated Core/Hub instances and checks that explicit close and return make the old resource URL return 403. It also drops or delays actual issue responses, then verifies closure without a second issue or a reopened iframe; it does not fake a successful server receipt. It also loses real draft and confirmation responses, reloads/remounts the panel, delivers an old same-operation query from another tab, and verifies one linked Core task with one draft POST and one confirmation POST. A request dropped before arrival stays unknown on 404; explicit reconciliation creates a durable fence and rejects the late original request. The current local result and source hashes are in [preview-recovery-test-results.json](preview-recovery-test-results.json). No production service or AI provider is used. Intent lifecycle and authorization tests are in `tests/preview-access-intents.test.mjs`; mock failure/race coverage remains in `tests/e2e/preview-ui.mjs`.

## Isolation and bounds

The preview is served on the existing Hub HTTPS origin, including IP-only deployments; no new DNS name, public port, or local development port is required. **Every asset response** has CSP sandbox, including SVG and HTML with uppercase extensions, so opening an asset at top level never creates a same-origin document that can read Hub cookies, APIs, or desktop storage. HTML has `sandbox allow-scripts allow-forms` without `allow-same-origin`, plus a restrictive script/style/image/font allowlist for the serving origin, `connect-src 'none'`, and `form-action 'none'`. Non-HTML assets have a stricter no-script sandbox; unknown MIME types are attachments. Browser code has an opaque origin and cannot read the Hub's account Cookie or CORS-protected API. Only static non-HTML assets under a valid preview capability answer `Access-Control-Allow-Origin: null`, allowing Vite ES modules, CSS, SVG images, and dynamic imports to load from the sandbox. No general Hub API receives that CORS permission. Capabilities are scoped to one build and account session, stored hashed, expire after ten minutes, and can be revoked in the `preview_caps` table. Every resource request also checks that the session, account owner subject and project access are still active.

The node link uses bounded 16 KiB chunks. Hub checks the registered asset size and SHA-256 before returning bytes, with a 4 MiB file limit, 16 concurrent Hub requests, 8 node reads and a five-second request timeout. Every request checks current node epoch and project ownership. Node disconnection fails pending requests; no preview request joins the durable task command queue. Unsupported backend calls fail under CSP rather than receiving invented API data. A real backend requires a later explicit per-project route/method/target registration and separate tests.

Build import rejects `.map` files (including case and trailing whitespace variants) and any asset containing a `sourceMappingURL` directive, whether external or inline `data:` and in JS or CSS comment form. The bounded scan is at most 4 MiB per file and 32 MiB per build. This excludes source maps carrying extra original source text; it does **not** make the served JavaScript itself confidential.

## Verification boundary

`tests/preview-contract.test.mjs` builds a real Vite production bundle, exercises registration, source/artifact identity, path and symlink rejection, Hub account filtering, capability and feedback idempotency, and runs the page in Chrome with a dynamic ES module import. `tests/preview-integration.test.mjs` uses actual Core, Hub and SQLite stores, registers the real build, verifies the local desktop bearer routes and Chrome dynamic imports, creates real tasks from both local and Hub feedback, then simulates the persisted confirming crash window and a lost Hub receipt: after Core restart, confirmation is refused as unknown and explicit reconciliation finds the original task without creating another. This integration test does not restart the Hub; actual Hub restart recovery is covered by the dedicated feedback-recovery test. These are local tests. Root still needs to run the complete phone UI workflow. An active browser session alone is not evidence that a real backend is present.

## Controlled build candidate (in development; not accepted)

This section describes the current controlled-build candidate in `server/preview/controlled-build.mjs`, `server/preview/registry.mjs`, `server/preview/node-link.mjs`, and `server/hub/preview.mjs`. It does not replace or reinterpret the legacy `POST /api/preview/builds` import route above. An isolated browser flow using real Core/Hub/worker has passed build, exact-preview open, and one explicit feedback-task confirmation; final package, phone, and broader recovery acceptance remain pending.

The first profile is the fixed `vite-vanilla-v1` profile. It accepts the constrained static source view defined by `server/preview/controlled-build-profile.mjs`; it does not load project scripts, project dependencies, or project configuration as build configuration. `apiTarget` is either `static` or the isolated `records-v1` interface. `records-v1` provides this preview's bounded record persistence; it is not an arbitrary project business API or URL proxy. `dataMode` is `simulated` or `real`, and `real` is accepted only with `records-v1`; the label alone is not proof of a real data source.

### Local Core request identity

All routes below are owner-only local Core routes:

| Route | Identity and behavior |
| --- | --- |
| `POST /api/preview/controlled-builds` | Exact request fields: `{requestId,projectId,taskId,expectedRevision,contentVersion,worktreeId,profile,apiTarget,dataMode}`. `requestId` is the idempotency identity. Repeating the same ID and identical request returns the existing build record; reusing it with different fields is rejected. New work requires the task revision/content version, project/worktree path, selected node binding, and current authority to match. |
| `GET /api/preview/controlled-builds/{requestId}` | Reads the original request record and its state (`prepared`, `snapshot_ready`, `building`, `output_ready`, `registered_local`, `ready`, `failed_no_publish`, or `unknown`). The public result may include the original `previewId`, source/artifact digests, and a fixed error code; it does not expose local paths or credentials. |
| `POST /api/preview/controlled-builds/{requestId}/reconcile` | Empty body; operates only on that request. It may inspect the original private executor record or continue publication of the already built artifact. It must not prepare or spawn another build. If execution or registration cannot be proved, the result remains `unknown`. |

The managed manifest binds `previewId`, `projectId`, `taskId`, `contentVersion`, and `sourceTaskRevision`, plus source/artifact identities and fixed tool/profile provenance. Before sending a registration or registration-query frame, NodeLink synchronously rechecks task identity, node binding, and authorization against that original manifest. A first registration additionally requires the current task revision and `contentVersion` to still match; a historical registration query may use the original identity after a later task edit. At first Hub registration, the Hub rechecks the project grant and current owner node/epoch, then compares the fresh task snapshot's revision and `contentVersion` to the manifest. Later edits do not rewrite an already registered manifest: it remains historical provenance for the build-time revision/content version and does not imply that the current task is accepted.

Registration is idempotent only for the same `previewId` and the exact same full manifest under the same tenant, node epoch, and project. A conflicting reuse is rejected. If the registration response is lost, Core queries `registration-query` with the original `previewId` and full manifest. `found:true` confirms only that matching stored registration; `found:false` means no matching registration is currently stored, not that the earlier build failed. After rechecking current binding and authority, Core may register only that same manifest under the same `previewId`. A missing query response remains `unknown`. It must never turn an unknown result into a second `requestId`, `previewId`, or build.

Before publishing or making the artifact available, the contract requires proof that the original MacJob was attempted and retired, and that its private record matches the request, workspace, and fixed Python executable. A lost or mismatched record must remain fenced as `unknown`; it cannot be treated as a successful exit. FIX396 added historical-record, original-record and controlled-build regressions (7/7, 18/18 and 6/6), plus a live Core/Hub case for the current registration-query/sourceTaskRevision/beforeSend flow; REVIEW397 reported no unresolved P1/P2 in its reviewed scope. The live case injected local `markRegistered` persistence failure after Hub registration, edited only task revision, then queried and recovered the original registration and read its HTML/JS. It did not inject wire-level response loss. PACKAGE401 additionally passed resource probes and a packaged Core/Hub/Python/Vite controlled-build/read/query-recovery flow in an isolated ad-hoc signed app, including PTY Unicode write and tmux detach preservation. The app's native window/menu was not exercised and the package was not formally signed/notarized. These results are bounded: the old-boot retired-record scenario was simulated rather than a real Core restart, and `readJobRecord`, `recover`, and signal identity remain strict to the current boot. The tests do not establish physical-phone acceptance; see [controlled-build evidence](controlled-preview-build-test-results.json).

An `unknown` status means the system cannot prove whether the original operation completed; it means neither “failed” nor “safe to resend.” HTTP request identity and Hub registration identity remain separate: query the original `requestId` for Core state, and use the original `previewId` plus full manifest for Hub registration recovery. Do not start a replacement build until the original outcome is conclusively resolved by the owner flow.

# 产品设计 v0.1

状态：提案。产品名暂定“推进”。

## 1. 产品定位

一个跨 AI 工具的任务进度与验收中心：平时安静地悬浮在桌面，需要时展开查看过程，也能从手机查看和继续任务。

它保存三类信息：用户真正要什么、AI 实际做了什么、哪些结果已经得到验证。界面只露出当前需要知道的部分。

默认使用场景：用户让 AI 开发一个多功能项目，中途切换对话或模型，也可以离开电脑。回来后，无需翻聊天记录，就能理解进度并决定下一步。

## 2. 从一句需求到一项可验收的工作

1. 用户选择项目目录并连接 AI 工具，看到具体接入能力：可读进度／可写任务／可继续任务。
2. 对话提出需求后，AI 生成任务草案，保留来源对话和原始需求引用。
3. 将需求归入项目整体任务，避免每轮对话重复建单。用户可以修改，重要范围变化突出显示。
4. 每个任务写清“期望结果”和“怎样算完成”，再开始执行。常规任务不需要反复确认；会改变目标、交付形式或成本上限的变更单独展示。
5. 执行过程中更新当前步骤、阻塞原因和可核对的产物。AI 一轮结束并不等于任务完成。
6. AI 提交结果后进入待验收。测试和人工检查依据预先定义的标准进行，符合条件才进入已完成。
7. 新对话读取项目交接摘要，继续已有任务。手机上的继续操作同样带着这一份上下文。

## 3. 任务信息：首屏一句话，展开有依据

列表每条任务只展示：名称、状态、一句话进展，必要时补上负责人和异常标记。

例如：

> 订单列表接入 · 进行中 · 列表已可展示，但仍使用示例数据，尚未连接订单系统。

点开任务后默认四块：

| 内容 | 展示方式 |
| --- | --- |
| 原本要什么 | 一句话描述结果，附一个真实使用例子 |
| 现在做到哪 | 一句话说明实际状态和剩余缺口 |
| 怎么实现 | 简短说明方案、选择理由和主要取舍；技术细节继续展开 |
| 如何验证 | 验收条目、检查结论、证据以及下一步 |

“实现思路”记录可解释的方案与决策摘要，不要求公开模型内部的完整思维过程。源代码路径、日志、命令、截图和完整测试报告放到第二层，避免占满界面。

任务维护者和 AI 写入 `summary` 时，先用普通用户能理解的一两句话说明“现在能做什么、还不能做什么”；写入 `nextStep` 时说明接下来要做的具体动作。不要用文件名、命令退出码、租约或协议名称代替交付说明。比如写“手机已能让电脑修改代码并查看结果；断网后能否安全恢复还在验证”，对应命令、文件改动和检查记录放进证据。摘要是当前记录，不自动代表功能已验证或已获人工验收。

示例：

> 原本要：在现有后台里查看真实订单，刷新后状态仍然一致。实际结果：页面布局已做好，但数据来自本地样例。下一步：接入订单接口，再用新订单验证列表更新。

## 4. 状态与进度

主列表保留用户要求的三组；底层将执行和验收分开。

| 界面分组 | 内部情况 | 补充标记 |
| --- | --- | --- |
| 待完成 | 尚未开始、依赖未满足 | 等待前置任务 |
| 正在完成 | 执行、暂停、限额等待、阻塞、结果已提交但未通过验收 | 运行中／等待额度／待确认／待验收／存在偏差 |
| 已完成 | 当前需求版本的必要验收全部通过，无未解决的阻断问题 | 自动检查通过／人工确认；两者来源可见 |

取消和归档单独保留记录，不冒充完成，不再占用当前任务列表。失败是可重试状态，显示原因；离线和长时间无更新标记为状态未知，不猜测已经完成。

不提供随意拖到“已完成”的假进度。手动接受例外时，保留未满足条件，标记“例外接受”，默认不计入严格验收完成数。

默认显示“8 项中 3 项已验收”，不显示 AI 随口估算的 90%。父任务按叶子任务或其自身验收条件聚合，避免父子重复计数。若采用权重，由计划阶段确定；新增／删除任务记录基线变化，不能静默缩小分母。

## 5. 偏差检测：用原始要求检验交付

每个任务开始前保存一份有版本的验收约定：

- 预期交付物：设计稿、演示、真实集成、可部署应用或正式发布。
- 使用入口：独立页面、现有系统菜单、桌面入口或手机入口。
- 数据要求：允许样例、测试环境真实接口、生产数据；不能混为一谈。
- 用户路径：例如“登录后两步内看到订单并完成筛选”。
- 支持环境、失败状态、数据持久化和需要的验证证据。

判定分成三种，措辞明确：**已确认不符、疑似偏差、缺少证据**。没有证据不直接判定 AI 作假；检查未通过也不等于可以推断 AI 的动机。

| 可能出现的问题 | 如何发现 | 用户看到的提示 |
| --- | --- | --- |
| 用离线 demo 代替系统接入 | 对照交付类型、入口、接口请求和真实环境测试 | “要求接入现有后台，目前只有独立演示页” |
| 静态样例冒充真实数据 | 新建记录后读取，检查请求来源与持久化 | “页面可展示，但新增订单未出现在列表” |
| 测试通过但用户用不了 | 从用户入口执行完整场景，检查空态、失败态、权限和手机操作 | “接口检查通过，手机端提交按钮仍被遮挡” |
| 操作繁琐 | 预先约定步骤预算，人工体验与自动场景相结合 | “约定两步完成筛选，实际需要五步” |
| 无关功能挤占主要目标 | 将任务和产物映射到原始需求，识别遗漏或多余范围 | “通知设置已完成，核心导出功能尚未开始” |
| 旧报告支撑新代码 | 证据绑定需求版本、代码版本或文件摘要、运行环境 | “代码更新后尚未重新验证” |

检查顺序：确定性规则 → 可重复运行的集成／端到端验证 → 独立审查 Agent → 用户体验判断。模型意见单独呈现，不能代替成功运行的事实。对于设计、写作等任务，使用相应的验收清单与人工评审，不强套代码测试。

偏差卡片只写“要求 → 实际 → 影响 → 建议下一步”。“生成修复任务”先生成范围明确的任务；是否立即执行遵循项目已有自动化授权，不擅自扩大权限。

## 6. 三种界面

### 桌面主界面

左侧为项目与接入管理，中间为紧凑任务列表，右侧按需展开任务详情。默认把需要用户处理的偏差／审批和正在进行的工作放在前面，已完成任务可折叠。

项目视图汇总整体；“本次对话”只筛选这次对话新增或推进的任务，不复制任务。一个任务可以被多轮对话、多种模型接力完成。

视觉采用系统字体、充足留白、连续圆角、浅分隔线和克制阴影。状态同时有文字与图标，不依赖红绿颜色。浅色和深色均保留清晰对比，遵循减少动态效果设置。按钮命名使用“继续任务”“查看偏差”等直接动词。

### 悬浮窗

默认约 320–380 像素宽，只展示项目名、当前步骤、验收计数、需要处理的问题。点击展开详情；可拖动、贴边、收起、暂时隐藏。常驻托盘，支持快捷键唤出。

默认不抢焦点、不拦截其他软件键盘输入、不在每次更新时弹窗。通知只在完成、失败、需要决策或额度恢复后无法继续时触发；同类事件合并。全屏时可隐藏。

Ubuntu Wayland 下置顶和定位行为需要按桌面环境验证；若不支持，则使用普通紧凑窗口与托盘菜单，明确显示限制。基础任务查看和协议接入不能依赖全局按键注入。

### 手机

第一版使用响应式网页／PWA，从浏览器访问自己的服务器地址；后续有实际需求时再包装原生 App。首屏显示项目、最新同步时间、电脑在线状态与异常，任务详情全屏展开。

手机可查看结果、补充需求、暂停或继续已授权任务。继续按钮始终显示目标电脑、AI 工具和任务；按钮反馈区分“已提交”“电脑已接收”“AI 已开始”，不能点击后立刻假装执行成功。

电脑离线时仍可查看已同步的快照，但明显显示更新时间。默认不积压自动执行指令；用户明确选择排队后，命令有有效期，过期或任务已变更则不执行。电脑关机或睡眠时，服务器不会自动获得电脑算力；若要持续运行，需要另外配置服务器执行节点。

## 7. 跨 AI 接入

采用分级能力，不承诺所有工具具有同样控制能力：

1. **文件接入**：能读写项目文件的 AI 可读取背景并提交结构化更新；缺少心跳时只表示最近报告状态。
2. **MCP 接入**：AI 可读取任务、提交计划、汇报进展和附加证据。是否每轮调用仍取决于宿主配置和实际行为。
3. **原生适配器**：订阅执行事件、辨认运行和限额状态、按指定会话继续；能力由各工具的公开接口决定。

Codex 优先做原生适配器和通用文件协议。Claude Code 后续可用 hooks 辅助采集，Cursor 先用 MCP；监控能力和主动继续能力分别验收。普通网页聊天工具没有受支持接口时，仅支持手动／文件导入，明确标注。

## 8. 自动继续与插件

自动继续作为独立插件，和任务清单共享项目 ID、任务 ID、会话 ID、权限与事件。用户为选定任务启用一次策略，包括允许恢复的原因、次数、预算和有效时间；任意时刻可以停止。

恢复前确认：任务未完成、未被用户暂停、无待决审批、额度确实恢复、目标会话可用、没有另一执行器已经运行。恢复后等待 AI 开始事件；仅发送成功不能算恢复成功。

插件类别：AI 适配器、验收器、自动化策略、通知、远程连接、导入导出。核心承担任务身份、状态规则、权限与持久化；插件通过版本化接口添加能力，避免改一个功能就重写底层。

## 9. 多模型协作

角色围绕交付职责：产品规划、技术方案、实现、测试验收。CEO／CTO 等可以作为角色模板，但每个角色都必须产出具体决策或交付物，不为头衔增加对话。

默认只启用一个执行 Agent 和必要检查；复杂任务可开启独立审查。由单一协调器分配任务依赖和执行锁，避免多个 Agent 同时修改同一文件或重复花费。实现者不能改掉自己不满足的验收要求，也不能批准自己的人工验收项。

界面显示谁负责、采用了什么方案、审查结论与剩余分歧。协作有并发数、费用、时长和讨论轮数上限；无法收敛时呈现可选择的方案，由用户作决定。

## 10. 第一版范围与后续方向

第一版验收目标：三系统桌面看板、紧凑窗口、文件更新、Codex 真实事件、验收和偏差提示、项目交接、自动继续插件、可自托管的手机查看与受控继续。

内部按“本地闭环 → 原生接入与恢复 → 远程闭环 → 三系统发布”逐步验证；内部里程碑可以先完成单系统，但不能对外称为完成三系统首版。

后续扩展：Claude Code／Cursor 深度接入、独立验证 Agent、多执行节点、云托管、多用户协作、插件分发、原生手机 App。第一版保留协议和权限边界，暂不做插件市场与复杂计费系统。

优先补充的实用能力：任务停滞提醒、需求变更记录、证据过期提醒、一键项目交接、预算上限、可撤销的执行队列、备份和迁移。默认不显示排行榜、虚构生产力评分或满屏日志。

## 11. 产品是否真的完成的验收场景

- AI 新增一个任务后，看板无需手动刷新更新；关闭并重开后记录仍存在。
- AI 把“页面已完成”提交上来，但未接真实接口时，仍留在进行中并指出具体缺口。
- 用户新开对话，AI 能读到原始目标、当前任务、禁改约束和下一步，不重新规划重复任务。
- 额度恢复只继续指定会话一次；用户手动暂停后，计时器和手机请求均不能自动恢复。
- 两个 Agent 同时报进度，历史不丢失，版本冲突被显式解决。
- 手机重复点击继续、网络断开重连，不导致两个并行执行；无回执时显示未知。
- 同一个真实项目在 Windows、Ubuntu、macOS 上完成接入、更新、重启恢复与查看的基本流程。

## 12. 依据与边界

官方资料支持接入路线，但所有集成仍需以本机安装版本实测为准：Codex 的 [App Server](https://learn.chatgpt.com/docs/app-server) 提供会话与运行事件接口；Claude Code 的 [hooks](https://code.claude.com/docs/en/hooks) 可在生命周期节点触发处理；Cursor 支持 [MCP](https://cursor.com/docs/mcp)。这些接口不代表第三方程序已经能透明控制所有正在使用的桌面会话。

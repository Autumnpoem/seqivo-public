# Terminal protocol and integration contract

Status: implementation contract for the 2026-10-17 terminal work. This document describes required behavior; it is not evidence that any route, grant, stream, or mobile flow has passed a test. Local implementation may use different internal function names, but the trust and frame semantics below must remain the same.

## Boundaries and identity

The terminal path is `browser ⇄ Hub WSS relay ⇄ outbound node WSS ⇄ local core ⇄ trusted PTY/tmux adapter`. The browser never calls a local PTY or sends keys through `/api/commands`. The Hub authenticates the logged-in account, a separate browser device credential, the target node, and an explicit terminal grant. The local core checks a mirrored, node-issued grant again before opening a PTY or accepting input. Hub project grants, account owner status, the existing `remote-controller` role, and the local `viewer` token do not grant terminal access by themselves.

Decision: a dedicated WSS relay carries bounded interactive bytes because the existing durable command queue is designed for finite task actions and would replay or delay keystrokes. Outbound node WSS avoids exposing the desktop's SSH/HTTP listener to the internet. A separate device grant is required because the current account cookie resolves to one owner subject across browsers; account access alone cannot express which phone may use a terminal. These choices add a grant mirror and relay lifecycle to implement, but preserve the existing task command semantics and keep the desktop's core as the final input authority.

Identifiers are opaque strings except where stated. `tenantId`, `accountUserId`, `deviceId`, `nodeId`, `profileId`, and `connectionId` identify a terminal channel. A tmux `sessionRef` binds `nodeId + profileId + tmux server instance + tmux numeric session ID`; a display name is never an identity. An attachment has an increasing `epoch`, scoped to `connectionId`; switching targets, revoking access, or replacing the attachment increments it. All input and output carry the epoch. A node subject's existing `epoch` also fences revoked/repaired node credentials, but is distinct from attachment epoch.

The first profile is the ordinary OS user's configured shell/tmux server. Profile and project directory are opening preferences, not filesystem isolation. A plain shell attachment is ephemeral; tmux sessions persist after a client detaches. Do not kill a user's tmux server on browser close, node disconnect, or plugin shutdown.

## HTTP surface

All Hub `/api/terminal/*` requests require the existing account session cookie, `Cache-Control: no-store`, a same-origin `Origin` on state-changing requests, and the existing Hub Host/HTTPS checks. A legacy bearer subject cannot enroll a browser terminal device. The Hub creates a high-entropy, `HttpOnly; SameSite=Strict; Secure` (except loopback HTTP), host-only `terminal_device` cookie. Store only its hash. Browsers never choose their own `deviceId` or claim a grant via request body. Reject missing, malformed, duplicate, or mismatched cookies. Changing account association places the device in pending state again.

| Route | Request / response | Authority and effect |
| --- | --- | --- |
| `POST /api/terminal/devices` | `{label}` → `{deviceId, status:'pending', confirmationCode, expiresAt}` and device cookie | Logged-in account; rate limited. Pending enrollment visible locally. Code is short-lived and display-only, never terminal authority. |
| `GET /api/terminal/status` | `{device,nodes,grants}` | Account sees the current browser device and its effective grants. Online node metadata includes only profiles granted to this device; pending or absent devices receive no node/profile metadata. |
| `DELETE /api/terminal/devices/{deviceId}` | `{revoked:true}` | Logged-in account revokes one of its own devices and closes its active terminal sockets. |
| Local `GET /api/terminal/status` | `{enabled,profiles,grants,pendingDevices}` | Local `owner` token only. Hub pending device data may be unavailable; show that explicitly. |
| Local `POST /api/terminal/grants` | `{deviceId,profileId,scopes,confirmationCode}` → grant record | Local `owner` only; validate pending device belongs to logged-in tenant/account and matching code, then transmit grant to Hub over authenticated node channel. Scopes from `view`, `input`, `create`, `default`, `takeover`; never implied by board access. `takeover` independently authorizes takeover, return and control reconciliation. |
| Local `DELETE /api/terminal/grants/{deviceId}/{profileId}` | `{revoked:true}` | Local `owner` only; revoke locally first, notify Hub, and close active attachments. If Hub is unavailable, local denial remains authoritative and Hub must deny new tickets until synchronized. |
| `POST /api/terminal/tickets` | `{nodeId,profileId,scope:'view'\|'control',resumeConnectionId?}` → `{ticket,expiresAt,connectionId}` | Account and approved device cookie required. Node must be online; grant must include `view` and, for `control`, at least one of `input`, `create`, `default`, or `takeover`. Each action rechecks its own scope. Exact account/device/node/profile binding. Opaque 256-bit ticket, one use, 30 s expiry, stored hashed. No ticket in URL, cookie, logs, `Sec-WebSocket-Protocol`, or referrer. Resume ID must belong to the same active/recent connection. |
| Node `POST /api/node/terminal/grants` | authenticated node report | Node token and current subject epoch; Hub transactionally mirrors grant/revoke and closes affected browser streams. Hub must reject account or device mismatches. |
| Node `GET /api/node/terminal/pending` | `{devices,grants}` | Node token; pending device IDs and current mirrored grants for local approval/reconciliation. Confirmation code stays on the enrolling browser until supplied locally. |

Session listing and default changes use WSS `list` and `default` request/reply frames. The local broker persists defaults by account user + node + profile after verifying the live tmux identity. Keep local core routes before its `remote-controller` allowlist only if they explicitly require `owner`; an accidental fallthrough would give remote board commands local terminal authority. Local `startHttp` must use the existing local bearer check. A local browser terminal socket, if exposed, requires `owner`, exact allowed `Origin`, and the same frame checks.

## WSS upgrades and authentication

Use `/api/terminal/ws` for browsers and `/api/terminal/node` for desktop nodes. Hub validates allowed Host and exact Origin on every browser upgrade; an absent browser Origin is rejected. A node client may omit Origin but must authenticate with its current node bearer token. For browser WebSocket API compatibility, the browser first obtains a ticket over same-origin HTTPS and sends it in the **first WebSocket message** `{type:'auth',v:1,ticket}`. Node sends `{type:'auth',v:1,nodeId,token,profiles:[{id,label}]}` on its outbound WSS. The Hub replies `{type:'ready',v:1,nodeId,epoch,ownerUserId?}`; `ownerUserId` appears only when exactly one active account owner is bound to the node's tenant. Upgrade sockets have a short authentication deadline and a small unauthenticated connection cap; no terminal payload is processed before authentication. If a reverse proxy terminates TLS, the existing trusted proxy/public origin configuration remains the authority; do not trust arbitrary forwarded headers.

Ticket redemption is atomic. Check unused/unexpired ticket, current account session, device cookie hash, grant revision and scopes, node subject/epoch, and target profile. Bind the browser socket to those values, then remove ticket. Revalidate at every privileged operation, on periodic heartbeat, and when grant, account session, node, or device is revoked. Revocation handlers close affected sockets promptly and bump the relevant attachment epoch; heartbeat is a fallback for missed events. An authenticated node WSS is outbound from the desktop; it must never accept a node identity chosen only by the browser. Node token is never placed in a URL.

The Hub pings both browser and node sockets every 15 seconds and terminates a socket that has not returned a pong by the next tick. A resumed browser socket replaces the previous connection ID; frames from the old socket are rejected even before its close event arrives. Device status and stream access are rechecked against current grants. Browser network indicators alone do not establish link health.

## JSON frames (version 1)

Each WSS message is one UTF-8 JSON object, maximum 64 KiB encoded. Binary PTY bytes use base64 in `data`; decoded `input` and `output` chunks are at most 32 KiB. Unknown types/fields, bad values, oversized frames, and excessive rates fail closed with a bounded error and close where appropriate. Internal relay envelopes add `tenantId,nodeId,deviceId,profileId,connectionId,grantRevision,nodeEpoch`; Hub derives these from authentication, never trusts them from browser JSON. The node verifies the envelope against its local grant mirror on every open/input/create/default operation.

| Direction | Frame | Meaning |
| --- | --- | --- |
| browser → node | `{type:'open',v:1,connectionId,profileId,mode:'shell'\|'tmux',cols,rows,resumeOffset?,redraw?}` | Fresh tmux open attaches saved default only if the exact `sessionRef` is still live. No default returns `NEEDS_SELECTION`; no silent session creation. A resume opens the same current target only if connection ID, grant, and tmux identity still match. `redraw:true` reattaches the same tmux target after an output gap and advances epoch. Shell mode creates or resumes a broker-retained PTY; a gap must not restart its process. |
| browser → node | `{type:'list',v:1,requestId}` | Enumerate live tmux sessions; names are display-only. |
| browser → node | `{type:'select',v:1,requestId,sessionRef,epoch}` | Stop old input immediately; revalidate target; attach and redraw; increment epoch before `ready`. Old target remains running. |
| browser → node | `{type:'create',v:1,requestId,name,epoch,cols,rows}` | Explicit tmux create, then attach; requires `create` grant. Name validated as data and passed via argument array, never shell interpolation. |
| browser → node | `{type:'default',v:1,requestId,sessionRef}` | Persist exact live session identity; requires `default` grant. Does not switch current target. |
| browser → node | `{type:'input',v:1,epoch,seq,data}` | Requires `input` grant. `seq` strictly increases in current epoch; duplicate/late frames rejected. Decode size bounded; node writes once to current PTY only after final authorization and epoch check. |
| browser → node | `{type:'resize',v:1,epoch,cols,rows}` | Bound sizes (for example 20–300 columns, 5–100 rows); only current attachment. |
| browser → node | `{type:'detach',v:1,epoch}` | Close attachment client, retain tmux session. Plain shell may exit; report this to browser. |
| browser → node | `{type:'takeover',v:1}` / `{type:'return',v:1,notes?}` / `{type:'reconcile-control',v:1,action:'acquire'\|'release'}` | Requires the separate `takeover` grant and a control ticket. Return notes are at most 4000 characters. The local control authority performs process and writer checks before changing ownership. |
| node → browser | `{type:'ready',v:1,connectionId,epoch,sessionRef,cols,rows,offset,lastInputSeq?}` | Input may resume only after this frame. A same-epoch resume keeps the last accepted input sequence; `lastInputSeq` helps the browser avoid reusing it. |
| node → browser | `{type:'sessions',v:1,requestId,items,defaultRef}` | Each item has `sessionRef,name,attached`; no project or AI conversation claim. |
| node → browser | `{type:'output',v:1,epoch,offset,data}` | `offset` is the first byte offset in this attachment's stream; bytes decoded from base64. |
| node → browser | `{type:'inputAck',v:1,epoch,seq,status:'written'}` | Means accepted by PTY, **not** shell-command success. No ack or uncertain transport means unknown; never replay automatically. |
| node → browser | `{type:'gap',v:1,epoch,nextOffset}` | Output history was truncated; clear terminal view and request fresh attach/redraw. Never concatenate truncated ANSI bytes onto an old screen. |
| node → browser | `{type:'exit',v:1,epoch,reason}` / `{type:'error',v:1,requestId?,code,message}` | Explicit lifecycle/failure state; no raw secret or terminal output in logs. |
| node → browser | `{type:'control',v:1,managed,phase,reason,changes,owned}` | Public control state only. Hub forwards an allowlist of fields and strips authority tokens, including extra fields on change entries. |

### Input backpressure and one-attachment retirement

The browser admits one input callback atomically: at most 64 KiB of UTF-8 bytes may wait locally, split at Unicode scalar boundaries into frames of at most 16 KiB. It sends at most eight unacknowledged input frames on one socket, `connectionId`, attachment `epoch`, and control generation. It assigns `seq` when a frame is actually sent. Only a `written` acknowledgment for a sequence in that same attachment's unacknowledged set opens another slot. Socket loss, target/epoch/control change, transfer, output recovery, error, or disposal drops unsent bytes; sent but unacknowledged bytes remain uncertain and are never replayed. A confirmation dialog for paste also binds to the control generation and input-flow revision. Capacity rejection applies to the entire callback, without sending a prefix.

The Hub's authenticated node `ready` frame advertises `attachmentCloseV1:true`. A node that receives that capability may send `{type:'terminal-attachment-close',v:1,connectionId,code:'INPUT_OVERLOADED'}` on the node WSS. The Hub accepts only these exact fields from its current authenticated node and closes only the matching browser connection with a non-resumable error; the node invalidates every queued manager context for that connection before any final write check. The tmux server/session and other browser attachments remain running. `terminal-close` or `terminal-suspend` removes the node's retired-connection tombstone. If more than 64 tombstones accumulate without those notifications, the node closes the link fail-closed rather than silently reusing an ID or retaining unbounded state; that exceptional protocol failure affects other attachments.

For an older Hub without `attachmentCloseV1`, the node freezes that attachment locally and sends only existing nested terminal `error` and, when its epoch is known, `exit` frames. The old Hub cannot provide the new explicit browser-socket closure or guaranteed resource reclamation; upgrade Hub before node for the full behavior. The fallback must not send an unknown top-level frame that would close the whole node link. Neither flow-control acknowledgments nor attachment closure prove a shell command succeeded.

The Hub is a relay, not a PTY owner. Per attachment keep a bounded output ring (initial target: 1 MiB or 30 s, whichever is shorter), cap live connections per device/node, and terminate slow consumers rather than buffering without limit. The exact caps may be tightened by measured capacity. While disconnected, no new browser input is queued; resumption may replay **output only** from `resumeOffset` if all identity and epoch checks still pass. On buffer miss emit `gap`. A deliberate new connection uses default; a transient resume retains current target. Browser should drop all locally pending key events on socket loss and on epoch change. Race after a write but before `inputAck` is inherently ambiguous and must be shown as such.

## Local core and adapter seam

`GET /api/terminal/diagnostics` uses the existing loopback Core owner authorization. It returns at most 128 managed-record summaries plus one inventory failure, with fixed phase/category, timestamp and a record digest. It contains no commands, private paths or capabilities. The first cause is retained only for the current Core process, is not retroactive, and never grants control or clears an execution fence.

Managed pane identity checks use `nativeSelectedIdentities` to read the recorded supervisor, Shell and relay PIDs twice with exact birth seconds/microseconds, UID, parent and process group checks. This confirms only those live identities; it is not a full process inventory or a stop proof. Missing or replaced targets are rejected, and original tmux identity checks still surround the reads. Full process snapshots remain mandatory in the existing descendant, workspace-writer and parked-handoff checks. An unrelated process starting or exiting must not by itself invalidate the original three process identities; a failure of the full writer inspection still blocks the operation.

Suggested core integration is a `terminal` manager initialized after local store and remote identity are available, returned by `createCore`, and closed before plugin/store shutdown. Its operations are `status`, `grant/revoke`, `list`, `open/select/create/default`, `write`, `resize`, and `detach`. Every operation receives a trusted context created by local HTTP or authenticated Hub node envelope; raw browser fields cannot create that context. Core owns grants, attachment epochs, input sequence, default identity checks, stream bounds, and auditable metadata. The adapter owns actual PTY/tmux process lifecycle and must not grant access itself.

The runtime leaf's proposed shape fits: `createTerminalRuntime({shell,cwd,cols,rows,env,args,onData,onExit,maxChunkBytes}) → {pid,write,resize,close({terminate})}` and `createTmuxAdapter({executable,serverName,env,timeoutMs}) → {inspect,list,create,attachTarget}`. `inspect/list/create` must return a server-instance fingerprint and numeric session identity; `attachTarget` rechecks these before producing argv. `close({terminate:false})` detaches the attachment client, not the tmux session/server. An ephemeral shell cannot promise detach persistence. Use the trusted built-in adapter first; the current plugin RPC in `server/plugin-process.mjs` is finite request/reply and cannot carry high-frequency terminal bytes. Future plugin capability `terminal.adapter.v1` must register behind the core manager with a dedicated bounded stream, never receive unrestricted remote raw input or bypass grants.

Execution leases alone only exclude overlapping managed commands in a workspace; `paused`, lease expiry, or tmux detach do not prove the AI process and descendants stopped. Unmanaged manual tmux access is an independent permission. Managed task takeover blocks new AI scheduling, requests a stop, verifies the provider process tree and writers, and keeps an `unknown` state on failure. Release to AI seals human input and checks changed files/background writers. Ordinary terminal access does not imply a safe AI handoff.

## Evidence required before saying this works

Automated checks: cross-account/device/node denial; malformed and reused ticket; wrong/missing Origin; grant revoke on live socket; node epoch replacement; stale input epoch and duplicate sequence; default deleted/server restarted; output overflow gap; disconnect without input replay; tmux detach retaining process; plain-shell cleanup. Real operation: Mac PTY and tmux with two existing sessions, iPhone Safari and Android Chrome keyboard/selection/reconnect, then packaged desktop compatibility. Local tests alone verify only their exercised paths. No real-device or production result is implied by this document.

## Code facts behind this contract

- `server/hub/account-http.mjs` authenticates account session cookies and maps them to the owner subject. `server/hub/terminal.mjs` adds the separate browser-device credential and terminal grants.
- `server/hub/http.mjs` attaches the terminal HTTP routes and WebSocket upgrade handler. It checks Host/Origin for HTTP and requires TLS beyond loopback.
- `server/remote-client.mjs` runs node-initiated polling for snapshots and finite task commands and supplies credentials to `server/terminal/node-link.mjs`, which opens the outbound terminal WebSocket.
- `server/core.mjs` creates the terminal manager and control authority and restricts local terminal HTTP routes to the owner role. `server/plugin-process.mjs` still exposes finite RPC methods for plugins.
- `server/execution-leases.mjs` tracks reservation states. The terminal control authority additionally requires process and writer evidence before a managed project changes hands.
